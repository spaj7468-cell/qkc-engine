01 · quick start

Two tags and one call.

Drop the script into any page and point QKC.init() at a question bank. The widget brings its own CSS — nothing else to install, nothing to build, nothing to configure.

index.html

03 · api reference

Every function, every option, every field.

The whole public surface is one global object QKC (default export in ESM/CJS). Two layers: QKC.init() — the embeddable widget; QKC.engine() — the headless core. Everything is synchronous and pure: same input + same seed → same output.

QKC.init(options) → instance

Mounts a quiz widget. Injects its scoped CSS (<style id="qkc-engine-css">) once per document, clears the mount point, builds a seeded test from the bank and renders question one.

optiontypedefaultdescription
bankarray | objectrequiredQuestions: a flat array of items, { items: [...] }, or the nested container { grade: { subject: { quarter: [...] } } } — anything QKC.toArray() accepts.
elstring | Elementappended to bodyMount point: CSS selector or DOM node. Its content is cleared. If omitted (or not found), a new <div> is appended to body.
countnumber10How many questions to pick (min 1, capped at bank length).
seedstring | numbertime-basedPRNG seed. Strings are hashed with FNV-1a. Same seed + bank + count → identical quiz down to option order.
mode'normal' | 'exam' | 'sprint''normal'Flow of the quiz — see §06 Modes. Invalid values fall back to 'normal'.
theme'bw' | 'light' | 'dark''bw'Widget color scheme via data-theme + CSS variables — see §07 Themes.
lang'ru' | 'en'autodetectUI language. Autodetect: <html lang> → navigator.language → 'en'.
timePerQuestionnumber (sec)30Sprint countdown per question. On timeout the question is auto-advanced and counted as skipped.
titlestring'QKC'Header title inside the widget.
shuffleOptionsbooleantrueShuffle choice options (deterministically, from the seed). Set false to keep bank order.
onFinish(result) => voidnullFires when the quiz finishes, with the full result object (below). Exceptions inside are caught — a broken callback can't break the widget.
onAnswer(ev) => voidnullNew in 1.2.0. Fires whenever an answer is graded: normal → on “check”; sprint → on select/timeout; exam → once per item at finish. ev = { id, value, correct, skipped, item: { t, ty, tp } }.
documentDocumentglobalDocument to render into — for jsdom/tests or multi-window setups.

instance — what init() returns

membertypedescription
rootHTMLElementThe .qkc-root node — style it, measure it, query inside it.
mountHTMLElementThe resolved mount point (el or the created div).
restart(o?)() → instanceApply options (optional) and start over: question 1, empty answers, fresh seeded build.
update(o?)() → instanceApply options live — bank, mode, theme, lang, title, count, seed, timePerQuestion, onFinish, onAnswer — and re-render. This is how the demo switches above work.
destroy()() → voidStop timers; clear the mount (or remove it if the engine created it).
results()() → result | nullThe result of the current/last finished run — or a live score of the current attempt; null before any question is built.

result object — onFinish(r) / instance.results()

shape

{ correct: 7, // graded right wrong: 2, // graded wrong skip: 1, // left empty total: 10, pct: 70, // Math.round(correct/total*100) perTopic: { // per-topic breakdown 'Многочлены': { correct: 3, total: 4 }, 'Одночлены': { correct: 2, total: 3 }, … }, seed: 'spring-2026', // the seed this run was built with mode: 'normal' }

grading rule

An answer is compared to c through QKC.norm(): trim → lowercase → collapse whitespace → comma becomes dot, then exact string equality. So ' Paris ' = 'paris', and '3,5' = '3.5'. Nothing fuzzier than that — grading is deterministic and auditable. Empty/null → skipped.

Per-topic stats come from the tp field; items without a topic land under '—' internally and are omitted from the widget's topic table.

QKC.engine(bank) → eng — the headless core

No DOM, no widget — build tests and score answers yourself (custom UI, server-side grading, Node scripts, generators).

methodreturnsdescription
eng.build(opts?)testAssemble a test: filter the bank, seed the PRNG, shuffle, pick count items, shuffle each choice's options. opts = { grade, subject, quarter, topics[], count=10, seed } — quarter accepts a number or 'all'.
eng.score(test, answers)resultGrade answers = { [itemId]: value } against the test. Same norm() rule and result shape as the widget.
eng.validate(){ ok, errors[] }Structural audit of the whole bank (see rules in §04).
eng.count(filter?)numberHow many items match the filter.
eng.topics(filter?)[{ topic, count }]Topic histogram, sorted by topic name.
eng.bankbankThe bank it was created with.

test object — what build() returns

{ seed: 'spring-2026', filter: { grade: 7, subject: 'algebra', quarter: 1, topics: [] }, items: [{ id: 0, // index — the key in answers t: 'Раскрой скобки: (x+10)(x+7)', ty: 'choice', o: ['x²+17x+70', …], // shuffled c: 'x² + 17x + 70', // ⚠ strip before clients e: 'По формуле (x+p)(x+q)…', tp: 'Многочлены', q: 1, grade: 7, subject: 'algebra' }, …] }

typical headless flow

const eng = QKC.engine(OURI_BANKS); const v = eng.validate(); // { ok, errors[] } const test = eng.build({ grade: 7, subject: 'algebra', quarter: 1, count: 10, seed: 'spring-2026' }); // send to a client WITHOUT answers: const safe = test.items.map(({ c, ...i }) => i); // …collect answers {0:'x²+17x+70', 1:'20x³', …} const res = eng.score(test, answers); res.pct; // 0..100 res.perTopic; // { 'Многочлены': {correct, total}, … }

04 · bank format

A question is six fields. A bank is an array.

No DSL, no schema registry, no server. Plain JSON-serializable objects — the same format the QKC trainer ships its 42 823 questions in. If you can JSON.parse it, the engine can play it.

one item, annotated

{ "t": "Раскрой скобки: (x + 10)(x + 7)", // question text "ty": "choice", // 'choice' | 'bool' | 'input' "o": [ // options — choice only, ≥ 2 "x² + 17x + 70", "x² + 10x + 7", "x² + 70x + 17", "x² − 17x + 70" ], "c": "x² + 17x + 70", // correct answer (must be in o) "e": "По формуле (x+p)(x+q) = x² + (p+q)x + pq.", // explanation "tp": "Многочлены", // topic — filters + per-topic stats "q": 1 // optional: quarter inside a container }

Real item #0 of OURI_BANKS[7].algebra[1] — the bank loaded on this page.

fields

fieldtypemeaning
tstringQuestion text. Shown as-is (no HTML).
ty'choice' | 'bool' | 'input'Answer type — see §05.
ostring[]Options. Required for choice (≥ 2, must contain c). Ignored otherwise; bool auto-renders True/False.
cstringCorrect answer, compared via norm() (trim / case / whitespace / ,→.). For bool: 'true' or 'false'.
estringExplanation shown after checking (normal mode) — optional but your users will thank you.
tpstringTopic. Drives topics(), the topics filter and per-topic stats.

Three shapes of a bank

flat array

The simplest: [item, item, …]. Exactly what the playground and most embeds use.

QKC.init({ bank: [ … ] })

{ items: [...] }

An object wrapper — handy when a bank file also carries meta (title, version, …); the engine reads .items.

QKC.init({ bank: { items: [ … ] } })

nested container

{ grade: { subject: { quarter: [items] } } } — the QKC trainer shape. build() filters slice it by grade/subject/quarter/topic.

QKC.init({ bank: OURI_BANKS }) eng.build({ grade:7, subject:'algebra', quarter:1 })

Validation rules — exactly what QKC.validate() checks

  • Non-empty. bank is empty if there are zero items.
  • t — required, non-empty string.
  • ty — one of choice / bool / input.
  • c — required, non-empty.
  • choice — o required with ≥ 2 options, and c must be one of them.
  • bool — c must be 'true' or 'false'.

errors are actionable

QKC.validate([ { t: '', ty: 'nope', c: '' }, { t: 'Capital of France?', ty: 'choice', o: ['Paris'], c: 'Lyon' } ]); // → { ok: false, errors: [ // 'item#0: missing text (t)', // 'item#0: bad type (ty)', // 'item#0: missing answer (c)', // 'item#1: choice needs options (o)', // 'item#1: correct answer not in options' ] }

csv → bank in 10 lines

// t,ty,o,c,e,tp — options separated by "|" function csvToBank(csv) { const [head, ...rows] = csv.trim().split(/\r?\n/); return rows.map(line => { const [t, ty, o, c, e, tp] = line.split(';'); const item = { t, ty, c, e, tp }; if (ty === 'choice') item.o = o.split('|'); return item; }); } QKC.validate(csvToBank(text)); // audit first!

custom theme — 6 lines of css

/* add a fourth theme next to bw/light/dark */ <style> .qkc-root[data-theme="paper"]{ --qkc-bg:#f7f3ea; --qkc-fg:#201c14; --qkc-line:#c9c0ad; --qkc-muted:#7a715d; --qkc-soft:#ece5d4; --qkc-sel:#201c14; --qkc-selfg:#f7f3ea; --qkc-r:6px; } </style> <script> QKC.init({ bank, el:'#quiz', theme:'paper' }); // unknown theme → falls back to 'bw'; // but data-theme="paper" is still set, // so your variables win. </script>

why it never clashes with your page

All rules are prefixed with .qkc-root and injected once per document (<style id="qkc-engine-css">) — the widget neither reads nor writes your stylesheets. Host-page inheritance is cut at the root: it sets its own font-family, text-align, line-height and box-sizing. Ten widgets on one page share one stylesheet; each paints itself from its own data-theme.

Sizing: the root is max-width:600px; drop it in a flex/grid cell and it fills it. The site theme switch in the header of this page (dark/light/b/w) is the same idea applied to the docs.

10 · architecture

The whole engine, taken apart.

One ES5-compatible file, four layers, zero dependencies. This section is the guided tour: what each layer does, what literally happens between QKC.init() and the first rendered question, and why the same seed always produces the same quiz.

What literally happens, call by call

QKC.init(opts) resolves the environmentPicks document (option or global), resolves el (selector/node) or creates a mount div; unknown mode/theme/lang values fall back to safe defaults instead of throwing.
toArray(bank) flattens the bankArray → copy; {items} → .items; container → full traversal merging grade/subject/quarter into every item.
CSS is injected once<style id="qkc-engine-css"> with the whole .qkc-* sheet (~4 KB of the gzip budget). Tenth widget on the page reuses it.
validate(list) runs before anything rendersInvalid bank → the widget renders an error card listing up to 6 problems instead of a broken quiz. Empty bank → “Bank is empty”.
The seeded build runsseed (string → FNV-1a hash → uint32) feeds mulberry32; Fisher–Yates shuffle picks min(count, len) items; each choice's options are shuffled from the same stream. Same seed ⇒ byte-identical quiz.
render() draws one questionHead (title · mode chip · “Question i/N”), bar (progress, or a live countdown in sprint), topic chip, the control per ty (radiogroup / true-false / input), footer buttons per mode. Sprint starts a 100 ms setInterval.
One listener handles everythingA single delegated click handler on the root reads data-act/data-val; Enter in the input maps to the primary action. No per-button listeners, no virtual DOM — direct createElement calls.
Grading is norm() equalitytrim → lowercase → collapse whitespace → ,→., then ===. Fires onAnswer (timing depends on mode).
finish() assembles the resultCounts correct/wrong/skip, builds perTopic from tp, calls onFinish(result) inside try/catch, renders the result screen: big pct, ✓/✗/– counters, per-question dots, topic table, seed chip, restart button.
update()/restart()/destroy()update applies new opts and rebuilds (this is how live theme/mode/lang switching works); destroy stops the timer and clears or removes the mount — safe in SPA cleanup hooks.

Design decisions, honestly

Determinism

mulberry32 PRNG + FNV-1a hashing + Fisher–Yates: same seed → same quiz down to option order. Tests are reproducible, grading is auditable, bugs are replayable.

build({ seed:'x' }) ≡ build({ seed:'x' })

No dependencies, on purpose

Every “why not X” has the same answer: a quiz engine needs ~600 lines, not a dependency tree. Nothing to audit, nothing to break on major releases, 8.8 KB total.

package.json → "dependencies": {}

ES5-compatible source

No arrow functions, no classes, no transpiler. The only ES6 API used is Object.assign (one-line polyfill for IE11, if anyone still needs it). The source is the build.

src/core.js → dist/ (wrapper only)

Direct DOM, no vdom

One question is ~20 createElement calls and one delegated listener. Re-render per state change is instantaneous at this scale — React would cost 40× the bytes for the same 60 fps.

render() → root.textContent='' → build → append

Client-only, zero telemetry

No network calls anywhere in the engine — banks are your files, results are your callbacks, storage is your choice. Works from file://, offline, in a kiosk.

fetch: 0 · XHR: 0 · beacons: 0

a11y as a feature

role="radiogroup"/"radio" + aria-checked options, aria-live result announcements, visible focus, keyboard-complete flow, prefers-reduced-motion respected by the host docs.

Tab / Enter / Space — everywhere

Repository layout & size budget

files

12 · testing & quality

Small engine, serious tests.

Two suites run on every change — headless logic in pure Node, widget behavior in jsdom. No mocks of our own code: the DOM suite drives the real dist/ build with real clicks.

run them

npm test # = node build.mjs && node test/test.mjs && node test/dom.mjs node test/test.mjs # headless core, zero deps node test/dom.mjs # widget in jsdom

14 · faq

Straight answers.

Do I need a build step, bundler or framework?

No. dist/ is committed; a <script> tag is enough. Bundlers work too (UMD + ESM + exports map), but nothing requires them. The docs site you are reading is itself plain HTML/CSS/JS with no build.

I want my own UI. Is the widget optional?

Completely. QKC.engine(bank) is pure logic: build() gives you a test object, score() grades answers, validate()/count()/topics() introspect the bank. QKC.init() is a convenience layer you can ignore — it shares the same core.

Where do correct answers live? Can students cheat?

Client-side, inside your bank — like every offline-first quiz library. For graded exams, build the test server-side (the core runs in Node), strip c before sending items, and score on the server with eng.score() — see the recipe in §11. For practice widgets, cheating only cheats yourself.

How exactly are answers compared?

QKC.norm(): trim → lowercase → collapse whitespace runs → replace , with ., then strict string equality. ' Paris ' = 'paris'; '3,5' = '3.5'. No fuzzy matching, no regex per question — deterministic and explainable.

Same quiz every launch, or different every time?

Your choice via seed: a fixed string/number reproduces the exact quiz (questions and option order); omit it and the engine seeds from the clock. Reproducibility is the point — an exam variant must be replayable for auditing.

Multiple widgets on one page?

Yes — every init() is independent; the stylesheet is injected once and shared. Ten demos on this page prove it (hero, quick start, live demo, three type cards, three theme cards, playground).

React / Vue / Svelte / Angular / web components?

The widget is plain DOM with a destroy() — it fits any lifecycle. §09 has copy-paste wrappers for React (useEffect), Vue 3 (onMounted) and a framework-neutral custom element; Svelte's onMount/onDestroy and Angular's ngOnInit/ngOnDestroy follow the identical two-line pattern.

TypeScript?

No .d.ts yet (roadmap). The API surface is small and fully tabulated in §03; until typings ship, a 20-line declaration file covers it — the option and result shapes are documented field by field.

Any analytics, phones home, licenses to worry about?

Zero network calls in the engine; zero trackers on this site; MIT license for everything — engine, widget, docs, and the trainer's banks. Use it in commercial products without attribution (appreciated, not required).

How big can a bank get?

The QKC trainer runs 42 823 items across 147 grade×subject partitions on this exact format, on school-grade hardware, offline. Flattening and filtering are O(n) once per init; per-answer work is O(1). Beyond ~100K items per screen, split banks per grade/subject into separate files (lazy-load, recipe §11).

What does BETA mean here?

The API is stable and tested, but pre-1.0-style guarantees don't exist yet: minor versions may add options, and .d.ts/npm-registry publication are still in flight. Breaking changes, if ever, come with a major bump and a migration note.

Why qkc.js.org? What is this domain?

js.org grants subdomains to JavaScript-ecosystem projects (npm packages, libraries, tools). This site is the documentation of one such library — qkc-engine — and nothing else: no school catalogue, no unrelated content, no redirects. The subdomain follows js.org's naming guidance for project pages (repository name without its suffix, cf. their “foo-lib → foo” example); the request is public: js-org/js.org#12650. Until it merges, the mirror at spaj7468-cell.github.io/qkc-engine serves identical content.
